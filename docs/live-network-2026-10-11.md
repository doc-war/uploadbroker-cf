# Go 与 Workers 实际网络测试（2026-10-11）

结论：当前 Workers 部署已实际成功接收约 49 MB 图片，但本轮没有证明迁移后所有路径都会加速，也没有完成 49 MB 的完整去重、下载验收。1 MB、10 MB 的完整业务验收均通过。下一步优先考虑下载边缘缓存和上传暂存流程，再通过稳定网络复测。

## 条件与方法

- Go：`https://uploadbroker.dow-war.com`。
- Workers：`https://uploadbroker2.dow-war.com`，运行构建时间 `2026-10-11T07:28:44.328Z`。
- 本机 Windows，curl 8.13.0、HTTP/1.1，默认 TLS 验证。另用 Node fetch 核对过两个 health 均为 HTTP 200。
- 正式两轮测试时间：北京时间 15:42:44 至 16:01:11。
- 每个接口连续探活七次，第一条新建连接，后六条复用连接。后六条的总耗时取中位数。
- 上传串行执行，避免两个服务竞争同一客户端带宽。测试文件为有效的随机 RGB PNG，同一轮、同一体积在两个服务间逐字节相同。10 MB 调换了服务测试顺序。
- MB 为十进制：实际文件分别为 995,865、9,994,979、49,000,377 字节；49 MB 不代表对 50 MiB 上限的边界测试。
- 上传设 `expires=1`；重复上传核对 URL 是否复用；完整下载核对字节数和 SHA-256。
- 上传每次新建客户端连接。两次下载在同一 curl 进程复用连接，因此第二次下载同时包含连接复用和可能的 CDN 缓存影响。
- 每个大文件阶段有效样本很少，不计算 p95，不把单次耗时当成稳定性能指标。

## 探活

| 项目 | Go | Workers |
| --- | ---: | ---: |
| 首次完整请求 | 5.746 s | 5.729 s |
| 首次 TLS 就绪累计时间 | 5.451 s | 5.457 s |
| 复用连接后六次总耗时中位数 | 203 ms | 269 ms |
| 复用连接后六次总耗时范围 | 201–561 ms | 244–728 ms |

两版均正常。Workers health 每次查询 R2 的 `index/`，Go health 查询 SQLite 和存储驱动，所以该接口包含存储探活开销，不能单独代表到边缘节点的网络往返。

本机解析到 `28.0.0.42/43`，疑似经过代理或 TUN 虚拟网络；不能把该地址当作实际 Cloudflare 服务器 IP。响应的 CF-Ray 后缀均为 `NRT`。新建连接多数需约 5–6 秒，而 DNS 和客户端 TCP 连接阶段通常仅数十毫秒。Node fetch 两次新建连接探活也分别需要约 5.9、5.6 秒，不能仅将延迟归因于 curl。

## 上传总耗时

总耗时包含客户端连接建立、发送、服务处理和返回响应。

| 图片 / 操作 | Go | Workers |
| --- | ---: | ---: |
| 1 MB 首次上传，第一轮 | 12.84 s | 10.21 s |
| 1 MB 首次上传，第二轮 | 31.28 s | 27.04 s |
| 1 MB 重复上传，第二轮 | 28.22 s | 21.47 s |
| 10 MB 首次上传 | 77.48 s | 63.55 s |
| 10 MB 重复上传 | 37.77 s | 51.73 s |
| 49 MB 上传有效成功样本 | 未取得可用对比数据 | 96.06 s |

第一轮 Workers 1 MB 重复上传另有 8.60 秒成功样本，Go 对应请求未保留下可解析的结果，因此不将其构成完整对比。

10 MB 样本中，扣除客户端连接建立阶段后的总耗时，首次上传为 Go 72.12 秒、Workers 56.98 秒；重复上传为 Go 32.23 秒、Workers 46.31 秒。剩余时间仍包含传输、存储 I/O、响应等开销，并非 CPU 时间。

Workers 10 MB 首次请求的客户端发送完成时刻约为第 47.41 秒，收到首字节约为第 63.54 秒。49 MB 成功请求对应约为第 82.24、96.05 秒。客户端发送完成不能证明服务端已收齐文件，尤其在代理和缓冲存在时；不能据此精确计算后端处理耗时。

两版去重都需要接收完整文件。当前 Workers 接收文件过程中按 5 MiB 分片写入 R2 staging，完整哈希得到后才能检查索引；首次提交还需要从 staging 读取并写入正式对象。大文件去重虽避免正式对象重复保存，仍有暂存 I/O。Go 代码完整接收并计算哈希后查询 SQLite，命中则跳过存储驱动 Put。该实现差异值得优化，但本轮不足以量化它单独造成的延迟。

## 下载

1 MB 使用第二轮完整样本；10 MB 使用第一轮完整样本。

| 图片 / 操作 | Go 总耗时 | Workers 总耗时 |
| --- | ---: | ---: |
| 1 MB 第一次下载 | 34.57 s | 8.28 s |
| 1 MB 第二次下载 | 21.55 s | 1.46 s |
| 10 MB 第一次下载 | 51.40 s | 26.05 s |
| 10 MB 第二次下载 | 10.36 s | 82.58 s |

| 第二次下载首字节时间 | Go | Workers |
| --- | ---: | ---: |
| 1 MB | 137 ms | 548 ms |
| 10 MB | 103 ms | 3,043 ms |

所有上述完整下载的大小和 SHA-256 均一致。

Go 的第一次下载为 `CF-Cache-Status: MISS`，第二次为 `HIT`。Workers 响应没有该标头；结合 `src/worker.js`，当前每次读取都查询 R2 元数据和对象，没有显式使用 Cache API。首字节方面 Go 缓存命中有优势，但完整下载速度仍受网络带宽影响：1 MB 的 Go 命中请求首字节仅 137 ms，完整下载却需 21.55 秒。

建议 Workers 增加受签名与过期时间约束的边缘缓存，命中后减少 R2 访问。实现时仍需校验 URL 签名、URL 到期时间，并限制缓存 TTL 不超过资源有效期。依据：[Cloudflare Cache API 文档](https://developers.cloudflare.com/workers/runtime-apis/cache/)。本轮仅测量、分析，没有修改线上缓存逻辑。

## 失败记录与结论边界

第一轮测量脚本将 curl 的 HTTP `000` 直接写为 JSON 数字，导致部分失败输出解析错误，未保留对应 curl 错误详情。这是测试脚本问题，不是服务返回的业务错误。已修正为字符串解析，并补测。

第二轮记录到了：

- Go 49 MB：curl 35，SSL/TLS 握手失败，总耗时 9.35 秒，上传字节数为零，没有 HTTP 响应。
- Workers 49 MB：curl 55，发送连接中断，总耗时 114.50 秒，客户端记录发送约 12.21 MB，没有 HTTP 响应。

第一轮 Workers 49 MB 有 HTTP 200、业务 `code=0`、返回 size=49,000,377 的有效成功记录，但其重复上传和下载没有完成验证。后续稳定性还不能视为通过。没有 Workers 调用日志或 CPU 指标，无法将后续断连归因于 CPU 限额，也不能证明它与 CPU 限额无关。

网络波动明显：同一体积 Go 首次上传两轮差距超过两倍；Workers 10 MB 两次下载相差超过三倍。适合把这些数字用作本机此时的体验记录，不适合推广为所有用户的性能结论。应先处理连接路径稳定性，再在常用用户网络下多轮复测；排查 Worker 超限需另外查看调用日志和 CPU 指标。
