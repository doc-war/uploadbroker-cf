# 内容哈希性能记录

2026-10-10，Windows 本地 workerd / Miniflare。候选为 Workers 原生流式 SHA-256 与纯 JS 增量 XXH32；生产 XXH32 不依赖 WASM 或 BigInt。默认保留 SHA-256，可在 deploy/wrangler.jsonc 的 vars 中设置 `"content_hash": "xxhash32"`。

运行 `npm run bench` 可复现。每个算法先用 64 KiB 数据预热三次，再对 1/10/50 MiB 各测三轮，交替算法顺序。同一轮两算法使用相同随机内容，上传每轮使用新内容避免去重命中。结果包含三种测量：缓存数据上的独立计算（每轮五遍，表中除以五）、64 KiB 分块 HTTP 流式哈希、包含解析和本地 R2 的完整上传。整包缓存只存在于基准 Worker。

中位 wall time，单位毫秒：

| 测量 | 大小 | SHA-256 | XXH32 |
|---|---:|---:|---:|
| 独立计算 | 1 MiB | 6.14 | 7.95 |
| 独立计算 | 10 MiB | 52.94 | 68.61 |
| 独立计算 | 50 MiB | 273.87 | 22.30 |
| 流式哈希 | 1 MiB | 26.79 | 30.45 |
| 流式哈希 | 10 MiB | 219.70 | 259.21 |
| 流式哈希 | 50 MiB | 1096.14 | 838.53 |
| 完整上传 | 1 MiB | 135.85 | 131.68 |
| 完整上传 | 10 MiB | 1073.18 | 999.51 |
| 完整上传 | 50 MiB | 5119.18 | 4796.48 |

XXH32 的 50 MiB 独立计算三轮约为每遍 684.20、14.36、22.30 ms，波动非常明显。JIT 优化、采样开销及本地调度可能影响结果，尚未隔离原因。完整上传中位耗时改善约 6.3%，包含网络往返和本地 R2 磁盘操作，不能直接说明哈希 CPU 改善。

原始数据见 [benchmark-results.json](benchmark-results.json)。脚本还输出 Inspector CPU profiles，采样 active/idle 及 JS 哈希栈时间用于诊断；这些指标无法准确分摊原生、异步调用和运行时开销，均不等于 Cloudflare 计费 CPU。

这些结果证明候选实现可运行，但不足以证明 XXH32 更稳定地满足 Free 单次 CPU 限额，因此不直接更换默认值。两种算法均通过 50 MiB 上传及下载一致性测试；是否适合 Free 仍需部署后观察 invocation CPU time 和限额错误。

XXH32 key 加入字节数，去重额外核对记录大小。同大小内容仍存在 32 位哈希碰撞风险；下载一致性测试始终用独立 SHA-256 校验完整数据。

本地测试客户端关闭连接复用，以避开 Windows 本地模拟服务出现的连接重置；生产 Worker 未加入这项测试客户端配置。
