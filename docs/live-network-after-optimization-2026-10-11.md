# 缓存与分段直写优化后的线上对比（2026-10-11）

本次已确认新部署生效：Workers health.time 为 2026-10-11T09:22:08.183Z（北京时间 17:22:08）。下载缓存实际命中，两版 1/10 MB 完整上传、去重与下载校验通过，CF 49 MB 也通过。10 MB 上传有改善，但缓存下载总耗时仍受网络影响，尚不能证明所有访问都会更快。

## 测量条件

- Go：https://uploadbroker.dow-war.com；CF：https://uploadbroker2.dow-war.com。
- 本机 Windows curl，HTTP/1.1，TLS 默认校验；两个服务串行测试，同轮使用逐字节相同的有效随机 RGB PNG。
- 第一轮北京时间 17:23:49 开始，补测 17:31:37 开始。1/10/49 MB 实际为 995,865 / 9,994,979 / 49,000,377 字节；MB 为十进制，不等于 50 MiB 边界测试。
- 上传每次建立新连接；两次下载在同一 curl 进程复用连接。第二次下载同时受连接复用和缓存影响，不能把全部时间下降归因于缓存。
- 本机连接地址仍为 28.0.0.42/43，疑似 TUN/代理；CF-Ray 均指向 NRT。TLS 建立通常仍需约 5–6 秒。
- 请求上限 180 秒。补测脚本仅对 curl 35 且已发送字节为零的握手失败重试，最多两次，保留失败记录。表格总耗时为成功尝试耗时，未加上前面的失败重试。
- 去重比较完整响应 data；每次下载校验字节数与 SHA-256。样本少、带宽波动大，不计算 p95，也不把耗时视为 Worker CPU。

## 大文件与失败记录

第一轮 Go 49 MB 请求在 180 秒超时，客户端仅发送约 32.05 MB，没有 HTTP 响应，未完成文件上传；CF 同体积在握手阶段失败，上传字节为零。这些不能当作服务端完整处理耗时，也无法据此诊断 Worker CPU 超限。

补测 Go 返回 HTTP 400、code 40004、max size 20971520 bytes，说明当前部署图片上限为 20 MiB；不能用 49 MB 比较两版性能。

CF 实际接收 49,000,377 字节，首次上传 177.38 s，重复上传 114.27 s，完整响应元数据复用。首次请求 curl 到 168.28 s 才完成发送，177.37 s 收到首字节；这里的时间差不是精确后端处理时间。

首次下载尝试握手失败，无输出 body 文件；测试脚本因此报 ENOENT，在读取失败请求的结果时中断验证。已修正脚本为记录完整性失败并继续处理其他结果。该批第二次请求实际成功，MISS、总耗时 36.46 s，另行核对 49,000,377 字节和 SHA-256 均正确。
